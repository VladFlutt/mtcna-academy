# Lesson: Криптография для сетевого инженера

Чтобы пользоваться VPN, математика не нужна, но нужно понимать, какой строительный блок что делает. Иначе многочисленные параметры IPsec и TLS выглядят как магия.

### Симметричное шифрование

**Один ключ** шифрует и расшифровывает. Быстро, используется для самих данных.

- Алгоритмы: **AES** (ключи 128/192/256 бит), ChaCha20; устаревшие: DES, 3DES, Blowfish.
- Режимы: **CBC** (классический), **GCM** (шифрует **и** проверяет подлинность за один шаг, сегодня предпочтителен).
- Проблема: как обеим сторонам безопасно получить одинаковый ключ? Её решают два следующих блока.

### Асимметричная криптография (с открытым ключом)

У каждой стороны есть **пара ключей**: **открытый ключ**, который можно дать всем, и **закрытый ключ**, которым никогда не делятся.

| Вы хотите... | Используйте |
|---|---|
| Отправить секрет, который прочитает только Боб | Зашифруйте **открытым ключом Боба**; расшифровать может только его закрытый ключ |
| Доказать, что это написали вы | **Подпишите** **своим закрытым ключом**; любой проверит вашим открытым ключом |

Алгоритмы: **RSA** (2048 бит и больше), **ECDSA** / Ed25519 (эллиптические кривые, короче ключи при той же стойкости). Асимметричная криптография медленная, поэтому её используют для небольших вещей: ключей и подписей.

### Хеш-функции

**Хеш** превращает любые данные в отпечаток фиксированного размера: **SHA-256** даёт 256 бит.

- Одинаковый вход → одинаковый хеш; изменение одного бита → совсем другой хеш (**лавинный эффект**).
- **Односторонний**: из хеша нельзя получить данные обратно. Хеш **не шифрование**, ключа для «расшифровки» нет.
- Трудно найти два входа с одинаковым хешем (коллизии). **MD5** и **SHA-1** в этом смысле взломаны.

**HMAC** это **хеш с ключом**: hash(ключ + сообщение). Получатель, знающий ключ, вычисляет его заново. Он доказывает **целостность** и то, что отправитель знает ключ. IPsec и TLS используют HMAC-SHA256 и подобные.

### Цифровая подпись

1. Алиса вычисляет хеш сообщения.
2. Она шифрует (подписывает) хеш **своим закрытым ключом**.
3. Боб сам вычисляет хеш и проверяет подпись **открытым ключом Алисы**.
4. Если всё совпало, сообщение от Алисы и не было изменено.

### Диффи-Хеллман

**Диффи-Хеллман (DH)** позволяет двум сторонам договориться об **общем секрете** через небезопасную сеть, ни разу не передав сам секрет. Каждая сторона отправляет открытое значение; из открытого значения другой стороны и своего закрытого обе вычисляют одинаковый секрет. Подслушивающий видит только открытые значения.

IPsec и TLS используют DH для создания сеансовых ключей. **Группы** DH (modp2048, ecp256, ecp384...) задают размер и тип математики.

**PFS** (Perfect Forward Secrecy, совершенная прямая секретность): каждый сеанс использует **новый** обмен DH. Если долговременный ключ украдут позже, записанный ранее трафик всё равно не расшифровать.

> Поиграйте с хешами, AES и игрушечным RSA в симуляторе **Криптографическая песочница**.

# Lesson: PKI и сертификаты

Открытый ключ сам по себе не говорит, **чей** он. Атакующий мог бы дать вам свой ключ и заявить, что он принадлежит вашему банку. Это решает **сертификат**: документ, который связывает открытый ключ с именем и **подписан** тем, кому вы доверяете.

### Что внутри сертификата X.509

| Поле | Пример | Значение |
|---|---|---|
| Subject / **common-name (CN)** | vpn.example.com | Кому принадлежит сертификат |
| **subject-alt-name (SAN)** | DNS:vpn.example.com, IP:22.1.1.33 | Другие имена и адреса; клиенты проверяют именно это |
| Issuer | CN=example-ca | Кто подписал |
| Срок действия | not-before / not-after | Даты |
| Открытый ключ | RSA 2048 | Ключ |
| **key-usage** | tls-server, digital-signature | Для чего можно использовать ключ |
| Подпись | ... | Подпись издателя над всем этим |

### Цепочка доверия

- **CA** (удостоверяющий центр) подписывает сертификаты. Его собственный сертификат **самоподписанный** (издатель = субъект).
- Клиенты хранят список **доверенных корневых CA** (браузеры и ОС поставляются с сотнями).
- Сертификат считается доверенным, когда цепочка подписей заканчивается доверенным корнем. Публичные CA часто используют **промежуточный** CA, поэтому вместе с сертификатом вы получаете файл **ca_bundle**.

**PKI** (инфраструктура открытых ключей) это вся система: CA, сертификаты, отзыв и правила вокруг них.

### Отзыв

Если закрытый ключ украден, сертификат нужно отменить до истечения срока. CA публикует **CRL** (список отозванных сертификатов) или отвечает на запросы **OCSP**. RouterOS умеет проверять CRL: `/certificate settings set crl-use=yes`.

### Откуда берутся сертификаты

1. **Публичный CA** (платный или бесплатный **Let's Encrypt**): ему автоматически доверяет любой клиент. Хорошо для SSTP и HTTPS для произвольных пользователей.
2. **Свой CA на RouterOS**: бесплатно и полностью под вашим контролем, но сертификат CA нужно установить на каждого клиента. Хорошо для IKEv2 road warrior и своих устройств.
3. **Отдельный самоподписанный сертификат**: быстро для тестов, каждый клиент предупреждает.

# Lesson: Сертификаты в RouterOS

### Строим свой CA, пошагово

**Шаг 1. Шаблоны.** `add` создаёт только шаблон, ничего ещё не подписано.

    /certificate
    add name=ca common-name=ca key-usage=key-cert-sign,crl-sign days-valid=3650
    add name=server common-name=22.1.1.33 subject-alt-name=IP:22.1.1.33 key-usage=tls-server
    add name=client1 common-name=client1 key-usage=tls-client

- **key-cert-sign** позволяет CA подписывать другие сертификаты, **crl-sign** подписывать CRL.
- **tls-server** / **tls-client** это расширенные назначения ключа для серверов и клиентов.
- Для сервера, к которому обращаются по DNS-имени, используйте `common-name=vpn.example.com subject-alt-name=DNS:vpn.example.com`. Имя лучше IP: адрес может измениться.

**Шаг 2. Подпишите сам CA** (так он становится самоподписанным):

    sign ca

**Шаг 3. Подпишите остальные с помощью CA:**

    sign server ca=ca
    sign client1 ca=ca

**Шаг 4. Проверьте флаги:**

    print

| Флаг | Значение |
|---|---|
| **K** | У маршрутизатора есть **закрытый ключ** |
| **A** | Authority (это CA) |
| **T** | Trusted (доверенный) |
| **I** | Invalid (недействительный) |
| **R** | Revoked (отозван) |
| **E** | Expired (истёк) |

**Шаг 5. Экспорт для клиентов:**

    export-certificate ca
    export-certificate client1 type=pkcs12 export-passphrase=ClientPass123

- Сертификат CA экспортируется **без** ключа (PEM). Клиентам он нужен только чтобы доверять серверу.
- Клиентскому сертификату **с** закрытым ключом нужна **export-passphrase**. **PKCS#12** (.p12) упаковывает сертификат и ключ в один файл, который Windows, macOS, iOS и Android импортируют напрямую.

Файлы появляются в **Files** (`cert_export_ca.crt`, `cert_export_client1.p12`).

### Импорт сертификата публичного CA

Обычно вы получаете три файла: `certificate.crt`, `private.key` и `ca_bundle.crt`.

    /certificate import file-name=certificate.crt passphrase=""
    /certificate import file-name=private.key passphrase=""
    /certificate import file-name=ca_bundle.crt passphrase=""
    /certificate print

После импорта ключа сертификат (с именем вроде `certificate.crt_0`) получает флаг **K**. Без K маршрутизатор не может использовать его для сервера.

### Let's Encrypt в RouterOS v7

    /certificate enable-ssl-certificate dns-name=router.example.com

Маршрутизатор запрашивает и продлевает бесплатный сертификат автоматически. Во время проверки TCP 80 должен быть доступен из Интернета, а DNS-имя должно указывать на маршрутизатор.

# Lesson: Имена сертификатов, отзыв и сертификаты для VPN

> Этот урок идёт по слайдам курса, глава 4 «Cryptography and PKI».

### Имя X.500 внутри сертификата

Сертификат это открытый ключ плюс имя, подписанные кем-то. Имя записано в форме **X.500**, и у каждого компонента есть двухбуквенный код:

| Код | Название | Параметр RouterOS | Пример |
|---|---|---|---|
| `CN` | Common Name, сама идентичность | `common-name` | `vpn.example.com` |
| `O` | Организация | `organization` | `Example Ltd` |
| `OU` | Подразделение | `unit` | `IT` |
| `L` | Населённый пункт | `locality` | `Riga` |
| `ST` | Регион или область | `state` | `Riga` |
| `C` | Страна, две буквы | `country` | `LV` |

Различайте три слова: **X.509** это формат сертификата, **X.500** это схема имён внутри него, а **CSR** (certificate signing request) это та же информация *до* подписи удостоверяющим центром.

> **Common Name важнее остального.** Клиент VPN сверяет CN или `subject-alt-name` с тем именем, по которому подключился. `O` и `L` это украшение, а неверный CN ломает соединение с ошибкой несовпадения имени.

### Отзыв сертификата: CRL

Сертификат действителен до истечения срока, если его не отозвать. CA публикует **CRL** (certificate revocation list), список серийных номеров, которые он больше не признаёт, и вторая сторона этот список проверяет.

    /certificate issued-revoke client1
    /certificate crl print

    /certificate settings set crl-download=yes crl-use=yes crl-store=ram

- **`crl-download`** загружает CRL, указанные в проверяемых сертификатах.
- **`crl-use`** собственно отклоняет отозванный сертификат. Загружать и не использовать это ничего не менять.
- **`crl-store=ram`** держит список в памяти, что и нужно на маршрутизаторе, флеш которого не хочется изнашивать.

Чтобы ваш собственный CA публиковал CRL, ему нужен **CRL host**, адрес, с которого список можно забрать, и задать его нужно **до того, как вы что-то подписали**:

    /certificate set ca crl-host=192.168.88.1

Этот адрес записывается внутрь каждого выпущенного сертификата как место, куда смотреть. Поменяете потом, и уже выпущенные сертификаты всё равно будут указывать на старый адрес. Это самая частая ошибка при самодельном CA.

### SCEP, когда устройств сотни

**SCEP** (Simple Certificate Enrollment Protocol) автоматизирует выдачу: устройство запрашивает сертификат у CA по HTTP, а CA либо выдаёт его автоматически, либо откладывает до подтверждения оператором. RouterOS умеет быть и сервером, и клиентом SCEP.

Это правильный ответ для парка устройств и неправильный для трёх маршрутизаторов, где `export-certificate` и `import` быстрее, чем поднимать сервис.

### Сертификаты в сервисах VPN

Где сертификаты реально применяются, с именами параметров со слайдов:

    /interface sstp-server server set certificate=server verify-client-certificate=yes enabled=yes

    /interface ovpn-server server set certificate=server require-client-certificate=yes auth=sha1 cipher=aes256 enabled=yes

    /ip ipsec identity set 0 auth-method=digital-signature certificate=server remote-certificate=client1

Три схемы, которые нужно различать:

- **Только серверный сертификат.** Клиент проверяет сервер, сервер проверяет логин и пароль. Это обычный режим SSTP и L2TP/IPsec и то, как работает клиент Windows без дополнительной настройки.
- **Взаимные сертификаты.** `verify-client-certificate=yes` (SSTP) или `require-client-certificate=yes` (OVPN). Без сертификата, выпущенного вашим CA, никто не подключится, поэтому одного украденного пароля мало. Это ответ MTCSE для road warrior.
- **IPsec с цифровыми подписями.** Identity ссылается на сертификаты обеих сторон вместо общего ключа. Именно так аутентифицируется road warrior IKEv2 в следующем модуле.

### Порядок действий на клиенте Windows

Слайды проходят его целиком, и это то место, где студенты чаще всего ошибаются:

1. Экспортируйте CA как `.crt`, а клиента как `.p12`.
2. Скопируйте оба файла на машину с Windows.
3. Установите **сертификат CA в «Доверенные корневые центры сертификации»**, именно для *локального компьютера*, а не для текущего пользователя. В неправильном хранилище Windows не будет доверять вашему серверу.
4. Установите `.p12`, он попадает в **Личные** вместе с приватным ключом.
5. Создайте подключение VPN и для IKEv2 или SSTP выберите аутентификацию по сертификату.

Два сообщения об ошибке стоит запомнить:

- *«Подключение заблокировано политикой»* — почти всегда CA лежит в пользовательском хранилище вместо машинного.
- *Несовпадение имени* — CN серверного сертификата это не то имя, которое вы вписали в подключение.

### Лаба со слайдов

> **Лаба:** *Задайте CRL host на своём CA, выпустите клиентский сертификат, примените его в SSTP с проверкой клиента, затем отзовите.*

1. `/certificate set ca crl-host=<ваш адрес в LAN>` **до** подписи чего-либо нового.
2. Выпустите новый сертификат `client2` и экспортируйте его как `.p12`.
3. Поставьте `verify-client-certificate=yes` на сервере SSTP и подключитесь по сертификату.
4. `/certificate issued-revoke client2`, посмотрите `/certificate crl print`, включите `crl-use=yes` на стороне сервера и попробуйте снова.
