# Lesson: Что такое IPsec

> Этот модуль идёт по слайдам курса MTCSE, глава 6 «IPsec».

### Сначала одно предложение

**IPsec** (Internet Protocol Security) это набор протоколов для защиты данных, передаваемых по IP. Он умеет **подтверждать подлинность** отправителя (аутентификация), проверять **целостность** каждого пакета и **шифровать** его.

Четыре факта со слайдов, которые стоит запомнить:

- Он разрабатывался для **IPv6**, позже был включён и в **IPv4**. RouterOS поддерживает оба.
- Это **стандарт**, описанный семейством RFC: RFC 4301 (архитектура), RFC 4302 (AH), RFC 4303 (ESP), RFC 2408 (ISAKMP), RFC 5996 (IKEv2), RFC 4835 (алгоритмы) и другие.
- Он работает на **сетевом уровне**, на самом IP.
- Поэтому он защищает **любой** протокол поверх IP, и TCP, и UDP, а приложения его даже не замечают.

### Где он находится среди других защищённых каналов

| Уровень OSI | Протокол защищённого канала |
|---|---|
| Прикладной | S/MIME |
| Представления | SSL, TLS |
| Сеансовый | PPTP |
| Транспортный | AH, ESP |
| Сетевой | IPsec |
| Канальный | PPP |
| Физический | — |

Сравните с TLS: TLS защищает одно соединение приложения (ваш браузер и один сайт). IPsec защищает **всё** между двумя IP-адресами или двумя сетями, какие бы приложения там ни работали.

### Что он даёт

Три свойства со слайдов:

- **Конфиденциальность (confidentiality)**: данные **шифруются**.
- **Целостность (integrity)**: маршрутизаторы на каждом конце туннеля вычисляют **контрольную сумму или хеш** данных, поэтому любое изменение по дороге обнаруживается.
- **Аутентификация (authentication)**: стороны доказывают, кто они, с помощью **ключей, подписей и сертификатов**.

Это ровно свойства из модуля 1 и строительные блоки из модуля 4: симметричный шифр для конфиденциальности, HMAC для целостности, общий ключ или сертификат для аутентификации и Диффи-Хеллман для согласования ключей.

### Архитектура: одна политика, три протокола

Слайды рисуют IPsec как **политику безопасности IPsec**, которая использует три протокола:

| Протокол | Полное название | Задача |
|---|---|---|
| **AH** | Authentication Header | Защищает данные: аутентификация и целостность, **без шифрования** |
| **ESP** | Encapsulating Security Payload | Защищает данные: шифрование **плюс** аутентификация и целостность |
| **IKE** | Internet Key Exchange | Согласует ключи и параметры и аутентифицирует стороны |

То есть две группы: **AH и ESP защищают трафик**, **IKE готовит для них ключи**. А **политика** решает, какие пакеты вообще защищать.

### AH по шагам

- **AH** доказывает, что пакет пришёл от партнёра и что **ни один бит** защищаемой части не изменился по дороге.
- Он создавался **только для целостности**. Он **не** шифрует: любой на пути по-прежнему может прочитать данные.
- Это **IP-протокол 51**, описан в **RFC 4302**.
- RouterOS поддерживает для AH **SHA1, SHA2 и MD5**.

AH защищает и часть внешнего IP-заголовка. Поэтому **AH не работает через NAT**: NAT меняет адрес, и получатель видит изменённый пакет.

### ESP по шагам

- **ESP** даёт всё, что даёт AH, **плюс конфиденциальность**.
- Он шифрует **симметричным ключом**.
- Это **IP-протокол 50**, описан в **RFC 4303**.
- Аутентификация ESP в RouterOS: **MD5, SHA1, SHA2 (256 и 512 бит)**.
- Шифрование ESP в RouterOS: **AES** 128/192/256 (CBC, CTR и GCM), Blowfish, Twofish, Camellia и устаревшие **DES** и **3DES**.

Почти всегда вы будете использовать ESP. Выбирайте AES с SHA256 (или AES-GCM, который делает и то, и другое) и не трогайте DES, 3DES и MD5.

### Что каждый из них защищает в пакете

Начнём с обычного пакета: `IP | TCP | Data`.

**С AH:** `IP | AH header | TCP | Data`. Весь пакет **аутентифицирован**, ничего не зашифровано.

**С ESP:** `IP | ESP header | TCP | Data | ESP trailer | ESP auth`.

- `TCP | Data | ESP trailer` **зашифрованы**.
- От `ESP header` до trailer всё **аутентифицировано**.
- Внешний заголовок `IP` ESP **не** защищает, и именно поэтому ESP может проходить через NAT (упакованный в UDP 4500, см. NAT-T).

# Lesson: Транспортный и туннельный режимы

### Два способа применить AH или ESP

IPsec работает в одном из двух режимов, и неверный выбор это самая частая ошибка проектирования.

| | **Транспортный режим** | **Туннельный режим** |
|---|---|---|
| Что защищено | Только **данные** IP-пакета | **Весь исходный пакет**, включая заголовок |
| IP-заголовок | Сохраняется **исходный** | Добавляется **новый** внешний |
| Создаётся новый пакет | Нет | Да, исходный инкапсулируется |
| Типичное применение | Хост с хостом, или защита другого туннеля (L2TP, GRE, IPIP, EoIP) | Сеть с сетью (site to site), подключение удалённых компьютеров к VPN |

### Транспортный режим по уровням

1. Транспортный уровень: `TCP | Данные`.
2. IPsec добавляет свой заголовок, и `TCP | Данные` **шифруются**: `IPsec | TCP | Данные`.
3. Сетевой уровень ставит впереди **исходный** IP-заголовок: `IP | IPsec | TCP | Данные`.
4. Канальный уровень оборачивает в кадр: `PPP | IP | IPsec | TCP | Данные | PPP`.

Три следствия со слайдов:

- Используется исходный IP-заголовок.
- Адреса оконечных устройств остаются без изменения.
- Новый пакет не создаётся.

### Туннельный режим по уровням

1. Сетевой уровень: `IP | TCP | Данные`, весь исходный пакет.
2. IPsec шифрует **его целиком**, вместе с заголовком: `IPsec | IP | TCP | Данные`.
3. Впереди ставится **новый IP-заголовок**: `Новый IP | IPsec | IP | TCP | Данные`.
4. Канальный уровень оборачивает в кадр: `PPP | Новый IP | IPsec | IP | TCP | Данные | PPP`.

Это **инкапсуляция**: исходный пакет со своими частными адресами едет внутри нового пакета между двумя публичными адресами.

С ESP разница выглядит так:

    Транспортный: IP HDR       | ESP HDR | Data          | ESP Trailer | ESP Auth
    Туннельный:   New IP HDR   | ESP HDR | IP HDR | Data | ESP Trailer | ESP Auth

В туннельном режиме исходный IP-заголовок лежит внутри зашифрованной части, и в интернете даже не видно, какие хосты общаются.

### Разбираем пример со слайдов: какой режим нужен двум офисам?

Схема со слайда:

- **Левый офис**: LAN 192.168.1.0/24, ПК 192.168.1.2, WAN маршрутизатора 2.2.2.2/30, маршрут по умолчанию через 2.2.2.1.
- **Правый офис**: LAN 192.168.2.0/24, ПК 192.168.2.2, WAN маршрутизатора 3.3.3.2/30, маршрут по умолчанию через 3.3.3.1.

**Шаг 1: маршрутизация без IPsec.** ПК отправляет `DATA | TCP | IP src 192.168.1.2 dst 192.168.2.2`. У левого маршрутизатора есть только маршрут по умолчанию в интернет, туда он пакет и отправляет. Интернет понятия не имеет, где 192.168.2.0/24: частные адреса не маршрутизируются. **Пакет потерян.**

**Шаг 2: неправильная схема, транспортный режим.** Слайд помечает её красным. В транспортном режиме маршрутизатор сохраняет **исходный** заголовок, поэтому в интернете пакет по-прежнему `IP src 192.168.1.2 dst 192.168.2.2`, зашифрованы только данные. Он всё так же не маршрутизируется. Транспортный режим нужен для трафика, **источник и получатель которого это сами партнёры** (хосты или маршрутизаторы, общающиеся между собой), а не целые LAN за ними.

**Шаг 3: туннельный режим, правильный ответ.** Левый маршрутизатор шифрует весь исходный пакет и добавляет **новый заголовок `src 2.2.2.2 dst 3.3.3.2`**. Такой пакет спокойно проходит интернет. Правый маршрутизатор снимает внешний заголовок, расшифровывает и находит исходный пакет `192.168.1.2 → 192.168.2.2`, который доставляет в свою LAN.

**Шаг 4: когда транспортный режим правильный.** Если два маршрутизатора сначала строят другой туннель между своими публичными адресами (например, L2TP между 2.2.2.2 и 3.3.3.2) и маршрутизируют LAN через него, то у каждого пакета, который видит IPsec, источник и получатель уже адреса самих маршрутизаторов. Транспортный режим просто шифрует этот туннель, и дополнительный заголовок не нужен. Это сценарий 2 дальше в этом модуле.

> **Простое правило:** LAN с LAN через два маршрутизатора → **туннельный режим**. Трафик, который начинается и заканчивается на самих партнёрах IPsec (включая другой туннель между ними) → **транспортный режим**.

# Lesson: IKE, ассоциации безопасности и две фазы

### Две группы протоколов

- **AH, ESP**: защищают передаваемые данные.
- **IKE** (Internet Key Exchange): управляет ключами.

### Что делает IKE

По слайдам IKE должен позволить двум сторонам:

- **аутентифицировать** друг друга;
- **сгенерировать и обменяться** общими ключами через публичную сеть, ни разу не передав сам ключ;
- договориться, **какой трафик** защищать (от какого отправителя к какому получателю);
- договориться, **какими протоколами** шифровать и какими аутентифицировать;
- установить **SA** (ассоциации безопасности) и определить параметры безопасности.

IKE использует **UDP-порт 500**. Когда между сторонами есть NAT, он переходит на **UDP 4500** (NAT traversal), и ESP упаковывается в тот же UDP 4500.

У IKEv1 для первой фазы **два режима** и **три метода аутентификации**:

- Режимы: **основной (main mode)**, 6 сообщений, идентичности защищены, и **агрессивный (aggressive mode)**, 3 сообщения, быстрее, но идентичность передаётся до включения шифрования; с общим ключом его лучше не использовать.
- Аутентификация: **общий ключ (pre-shared key)**, **шифрование открытым ключом**, **подпись открытым ключом** (сертификаты).

### Ассоциация безопасности (SA)

**SA** это термин IPsec для соединения. Свойства со слайдов:

- SA **однонаправленная**. Данные идут в обе стороны, поэтому SA всегда создаются **парами**.
- Одна пара создаётся **на каждый используемый протокол**: одна пара для AH, одна для ESP.
- У каждой SA есть уникальный номер, **SPI** (Security Parameter Index, индекс параметров безопасности), по которому получатель понимает, к какой SA, а значит к какому ключу, относится пакет.
- SA хранятся на **обоих** узлах. **Если на вашем маршрутизаторе есть SA, туннель установлен.**
- IKE создаёт SA **автоматически**.

В SA хранятся: SPI, адрес получателя, протокол безопасности (AH или ESP), алгоритмы, методы аутентификации, обмена ключами и шифрования, режим (транспортный или туннельный) и таймеры, например время жизни.

### Фаза 1 и фаза 2

IKE работает в две фазы.

**Фаза 1** строит защищённый канал **между двумя демонами IKE**:

- Создаётся **ISAKMP SA**, она же **IKE SA** или SA первой фазы.
- Используется основной или агрессивный режим.
- Стороны аутентифицируются по сертификатам или общему секрету.
- Согласуются: **метод аутентификации, группа DH, алгоритм шифрования, режим обмена, алгоритм хеширования, NAT-T, DPD и время жизни**.

**Фаза 2** использует этот канал, чтобы договориться о защите **пользовательского трафика**:

- Создаются **IPsec SA** (SA второй фазы), по паре на протокол.
- Согласуются: **протокол IPsec (ESP или AH), режим (туннельный или транспортный), алгоритм аутентификации, группа PFS (DH), время жизни**.
- Правильное завершение второй фазы приводит к появлению SA второй фазы, и на этом туннель считается **установленным**.

### Простая схема в четыре шага

1. **Трафик, который нужно защитить**, приходит на первый узел и совпадает с политикой.
2. **IKE фаза 1**: стороны аутентифицируются и строят защищённый канал связи.
3. **IKE фаза 2**: по этому каналу они согласуют IPsec SA, то есть туннель IPsec.
4. **Защищённый обмен трафиком**: идут пакеты ESP (или AH) с ключами из второй фазы.

### Где какая фаза живёт в RouterOS

| Что | Фаза | Меню RouterOS |
|---|---|---|
| Где другая сторона, режим обмена, passive | 1 | `/ip ipsec peer` |
| Как сторона аутентифицируется (PSK, сертификат, EAP) | 1 | `/ip ipsec identity` |
| Хеш, шифрование, группа DH, NAT-T, DPD, время жизни | 1 | `/ip ipsec profile` |
| Какой трафик защищается, туннель или транспорт | 2 | `/ip ipsec policy` |
| Алгоритмы ESP, группа PFS, время жизни | 2 | `/ip ipsec proposal` |
| Поднялась ли фаза 1? | 1 | `/ip ipsec active-peers` |
| Установлены ли SA? | 2 | `/ip ipsec installed-sa` |

> **Порядок поиска неисправностей:** нет активного пира → проблема фазы 1 (адрес peer, секрет в identity, алгоритмы profile, файрвол на UDP 500/4500). Активный пир есть, а установленных SA нет → проблема фазы 2 (подсети в политике, алгоритмы proposal, группа PFS). Обе стороны должны предлагать **совпадающие** алгоритмы.

# Lesson: IPsec в RouterOS: peer, identity и политики

### Пиры (peer)

    /ip ipsec peer

Настройки peer используются для установления соединения **между демонами IKE**. Затем это соединение используется для согласования ключей и алгоритмов для SA, и **с одним пиром может быть несколько SA**.

Поля, которые вам понадобятся:

| Поле | Значение |
|---|---|
| `address` | Адрес другой стороны. Может быть подсетью. |
| `local-address` | С какого адреса источника этот маршрутизатор общается с пиром |
| `profile` | Параметры фазы 1 (`default`, если не меняли) |
| `exchange-mode` | `main`, `aggressive` или `ike2` |
| `passive` | Ждать, пока другая сторона начнёт IKE; самим соединение не инициировать |
| `send-initial-contact` | Сообщить пиру, что старые SA нужно забыть, когда мы начинаем заново |

**Побеждает самый конкретный.** Если входящему адресу подходят несколько пиров, RouterOS берёт тот, у которого **самая длинная маска**: при пирах 2.2.2.0/24, /25, /26 и /27 соединение с 2.2.2.5 использует /27.

### Идентификация (identity)

    /ip ipsec identity

Identity говорит, **как** пир аутентифицируется. Пара маршрутизаторов со слайда:

| R2 (2.2.2.2) | R1 (1.1.1.1) |
|---|---|
| `/ip ipsec peer add address=1.1.1.1/32 name=peerR1` | `/ip ipsec peer add address=2.2.2.2/32 name=peerR2` |
| `/ip ipsec identity add peer=peerR1 secret=123123123` | `/ip ipsec identity add peer=peerR2 secret=123123123` |

По умолчанию `auth-method` это `pre-shared-key`. Секрет на обеих сторонах должен совпадать. В реальной жизни берите длинный случайный; `123123123` годится только для класса.

Два вопроса, которые слайды задают про эту пару, с ответами:

- **Кто к кому соединяется?** Оба пира знают адрес друг друга, поэтому IKE может начать **любая** сторона, как только у неё появится трафик для туннеля. Чтобы этим управлять, поставьте `passive=yes` на одной стороне: она будет только ждать.
- **Какие порты открыть в файрволе?** В цепочке `input`, от пира: **UDP 500** (IKE), **UDP 4500** (NAT-T) и **IP-протокол 50** (`ipsec-esp`). Протокол 51 (`ipsec-ah`) добавляйте только если используете AH.

### Проверка фазы 1: активные пиры

    /ip ipsec active-peers print

Результат первой фазы это **активный пир** в состоянии `established`, с аптаймом и числом SA второй фазы (`PH2 Total`). Если ничего нет, проверяйте по порядку: настройки peer, identity, profile (алгоритмы), затем файрвол filter.

### Политики: ЕСЛИ этот трафик, ТО это действие

    /ip ipsec policy

Таблица политик определяет, **применять ли** параметры безопасности к пакету. Читайте каждую политику как **ЕСЛИ (вкладка General) → ТО (вкладка Action)**:

**General (ЕСЛИ):**

- `src-address`, `dst-address`, `src-port`, `dst-port`, `protocol`: какие пакеты совпадают.
- `peer`: к какому пиру относится политика.
- `tunnel`: `yes` для туннельного режима, `no` для транспортного.
- `template`: это только шаблон для динамически создаваемых политик или нет.

**Action (ТО):**

- `action`: `encrypt` (защитить), `none` (пропустить без защиты), `discard` (отбросить).
- `level`: `require` (отбросить пакет, если SA ещё нет), `use` (отправить без защиты, если SA нет), `unique` (своя SA на каждую политику, нужно, когда несколько клиентов за одним адресом).
- `ipsec-protocols`: `esp` или `ah`.
- `proposal`: какой `/ip ipsec proposal` задаёт алгоритмы второй фазы.

На новом маршрутизаторе одна политика уже есть: шаблон `*T` с `::/0` на `::/0` в группе `default`. Им пользуются road warrior (модуль 7), для site to site он ничего не делает.

### Profile и proposal: алгоритмы

    /ip ipsec profile set default hash-algorithm=sha256 enc-algorithm=aes-256 dh-group=modp2048
    /ip ipsec proposal set default auth-algorithms=sha256 enc-algorithms=aes-256-cbc pfs-group=modp2048

Profile хранит фазу 1, proposal хранит фазу 2. **Обе стороны должны совпадать**: если один маршрутизатор требует SHA256, а другой предлагает только SHA1, согласование не пройдёт. На слайдах оба маршрутизатора оставляют proposal `default`, и это самый простой способ добиться совпадения.

### Проверка фазы 2: установленные SA

    /ip ipsec installed-sa print

Вы увидите SA с их SPI, источником, получателем, алгоритмами аутентификации и шифрования и размером ключа. Для одной политики site-to-site с ESP ожидайте **две** SA на каждом маршрутизаторе: по одной в каждом направлении.

# Lesson: Site to site, путь пакета и NAT

### Сценарий 1: туннельный режим между двумя офисами

Схема со слайда: **R2** с WAN 2.2.2.2 и LAN 192.168.2.0/24, **R1** с WAN 1.1.1.1 и LAN 192.168.1.0/24.

**На R2:**

    /ip ipsec peer add address=1.1.1.1 name=peer16
    /ip ipsec identity add peer=peer16 secret=1234567890
    /ip ipsec policy add peer=peer16 src-address=192.168.2.0/24 dst-address=192.168.1.0/24 tunnel=yes

**На R1:**

    /ip ipsec peer add address=2.2.2.2 name=peer19
    /ip ipsec identity add peer=peer19 secret=1234567890
    /ip ipsec policy add peer=peer19 src-address=192.168.1.0/24 dst-address=192.168.2.0/24 tunnel=yes

Читайте политики как зеркальные: `src` у R2 это `dst` у R1, и наоборот. Каждая политика ссылается на **свой** пир.

> На слайде у R1 тоже напечатано `peer=peer16`. Это опечатка: пир на R1 называется `peer19`, а политика должна ссылаться на пир, который существует на этом маршрутизаторе.

Затем ответьте на три вопроса со слайда:

1. **Сколько SA?** Выполните `/ip ipsec installed-sa print` на каждом маршрутизаторе: **две**, одна входящая, одна исходящая.
2. **Работает?** Пингуйте из 192.168.2.x в 192.168.1.x. Обычно **ещё нет**.
3. **Почему? SRC-NAT.** Это объясняет следующий раздел.

### Путь пакета с IPsec

У IPsec своё место в пути пакета RouterOS, и оно объясняет любое «не работает» в схемах site to site.

**Исходящий пакет (шифрование):**

1. Пакет из LAN проходит prerouting, решение о маршрутизации и цепочку **forward** как обычно.
2. Он проходит **postrouting**: mangle postrouting, **SRC-NAT**, очереди.
3. Только **теперь** маршрутизатор проверяет **политику IPsec**.
4. Если политика совпала: **шифрование IPsec**. Получается совершенно новый пакет ESP от самого маршрутизатора.
5. Этот новый пакет проходит **решение о маршрутизации** и путь **output** (RAW output, connection tracking, mangle output, filter output) и **второй раз** postrouting.
6. Затем уходит через выходной интерфейс.

**Входящий пакет (расшифровка):**

1. Пакет ESP приходит на адрес маршрутизатора, поэтому проходит prerouting и цепочку **input**.
2. После input маршрутизатор проверяет **политику IPsec** и **расшифровывает** пакет.
3. Расшифрованный исходный пакет возвращается в **начало** prerouting, как будто только что пришёл, затем идёт через маршрутизацию и **forward** в LAN.

Что это значит на практике:

- **Зашифрованный** пакет проходит `filter input` (входящий) и `filter output` (исходящий). Именно там нужно разрешить UDP 500/4500 и ESP.
- **Расшифрованный** пакет проходит `filter forward`. Именно там нужно разрешить трафик из удалённой LAN: `ipsec-policy=in,ipsec` совпадает ровно с пакетами, пришедшими через IPsec.

### Почему NAT ломает туннель

Посмотрите ещё раз на шаги 2 и 3 исходящего пути: **SRC-NAT происходит до проверки политики IPsec.**

На обоих маршрутизаторах обычно есть:

    /ip firewall nat add chain=srcnat out-interface=ether1 action=masquerade

Итак, по шагам:

1. 192.168.2.10 отправляет пакет на 192.168.1.10.
2. Masquerade меняет источник на **2.2.2.2**.
3. В политике `src-address=192.168.2.0/24`. Пакет теперь идёт от 2.2.2.2, поэтому **не совпадает**.
4. Пакет не шифруется. Он уходит в интернет с получателем 192.168.1.10 и **теряется**.

**Исправление со слайдов**: правило обхода NAT, поставленное **выше** masquerade:

    R2: /ip firewall nat add chain=srcnat action=accept place-before=0 src-address=192.168.2.0/24 dst-address=192.168.1.0/24
    R1: /ip firewall nat add chain=srcnat action=accept place-before=0 src-address=192.168.1.0/24 dst-address=192.168.2.0/24

`action=accept` в srcnat означает «не транслировать». `place-before=0` ставит правило первым, потому что правила NAT тоже проверяются сверху вниз.

**Более гибкий способ**, тоже со слайдов: использовать сопоставитель **IPsec Policy**, доступный в filter, NAT, mangle и RAW. Конфигурация RouterOS по умолчанию уже так и делает:

    /ip firewall nat add chain=srcnat out-interface-list=WAN ipsec-policy=out,none action=masquerade

`out,none` значит «только пакеты, которые **не** уйдут через политику IPsec». Всё, что будет зашифровано, пропускается автоматически, для любого туннеля, который вы добавите потом.

> **И FastTrack тоже.** Пакеты FastTrack пропускают проверку политики IPsec. Если ваша цепочка forward делает fasttrack установленных соединений, принимайте `ipsec-policy=in,ipsec` и `ipsec-policy=out,ipsec` **до** правила fasttrack, как это сделано в конфигурации RouterOS по умолчанию.

### Сценарий 2: транспортный режим защищает туннель L2TP

Второй сценарий со слайдов защищает уже существующий туннель:

- R2 (2.2.2.2) и R1 (1.1.1.1) строят **туннель L2TP** с адресами 10.1.1.2 и 10.1.1.1.
- R2 маршрутизирует удалённую LAN через него: `/ip route add dst-address=192.168.1.0/24 gateway=10.1.1.1`.
- R1 делает то же: `/ip route add dst-address=192.168.2.0/24 gateway=10.1.1.2`.

Каждый пакет L2TP в интернете и так идёт с 2.2.2.2 на 1.1.1.1, то есть между самими партнёрами. Поэтому достаточно **транспортного режима**:

    R2: /ip ipsec policy add peer=peer16 src-address=2.2.2.2 dst-address=1.1.1.1 tunnel=no
    R1: /ip ipsec policy add peer=peer19 src-address=1.1.1.1 dst-address=2.2.2.2 tunnel=no

(На слайде указан только `dst-address`; явный источник делает так, что политика совпадает только с трафиком между двумя партнёрами.)

Задайте те же три вопроса:

1. **Сколько SA?** Снова **две** на каждом маршрутизаторе.
2. **Работает?** Да.
3. **SRC-NAT?** Здесь проблемы нет: трафик LAN маршрутизируется в интерфейс L2TP, а не наружу через ether1, поэтому masquerade его не трогает, а пакеты L2TP и так несут публичные адреса.

Это та же идея, что и **L2TP/IPsec** для road warrior в модуле 7, только между двумя маршрутизаторами.
