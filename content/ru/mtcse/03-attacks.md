# Lesson: Атаки второго уровня

Атаки второго уровня идут **изнутри** LAN: гостевой ноутбук, заражённый ПК, устройство, которое кто-то подключил в свободный порт. IP-файрвол маршрутизатора большинство из них не видит, поэтому нужны настройки коммутатора и бриджа.

### MAC flooding

Коммутатор запоминает, какой MAC-адрес находится за каким портом, и хранит это в **таблице MAC (host table)**. Размер таблицы ограничен.

Как работает атака, пошагово:

1. Атакующий отправляет тысячи кадров со **случайными MAC-адресами источника**.
2. Таблица заполняется фальшивыми записями.
3. Настоящие хосты больше не запоминаются, и коммутатор **рассылает** их кадры во все порты, как хаб.
4. Атакующий перехватывает трафик, который ему не предназначался.

Защита: ограничьте число запоминаемых MAC на порт (port security на коммутаторах CRS), используйте 802.1X и не оставляйте включёнными свободные порты в общественных местах.

### ARP-спуфинг

ARP сопоставляет IP-адреса и MAC-адреса и не имеет аутентификации. Атакующий отправляет поддельные ARP-ответы: *«192.168.88.1 находится по МОЕМУ MAC»*. Жертвы отправляют трафик для шлюза атакующему (**man-in-the-middle**, «человек посередине»).

Защита RouterOS на интерфейсе LAN:

    /interface bridge set bridgeLAN arp=reply-only
    /ip dhcp-server set dhcp1 add-arp=yes

- **arp=reply-only**: маршрутизатор не изучает ARP-записи из сети, использует только статические.
- **add-arp=yes**: DHCP-сервер добавляет статическую ARP-запись для каждой аренды, поэтому DHCP-клиенты продолжают работать.

Маршрутизатор игнорирует поддельные ARP-ответы о хостах. (Клиентов всё ещё можно обмануть насчёт шлюза; на управляемых коммутаторах используйте DHCP snooping с ARP inspection.)

### Чужой DHCP и DHCP starvation

- **Чужой DHCP-сервер (rogue DHCP)**: кто-то подключил домашний роутер или неправильно настроил ПК. Клиенты получают **неверный шлюз или DNS**, случайно или чтобы перенаправить их.
- **DHCP starvation (истощение)**: атакующий запрашивает аренды с **множеством поддельных MAC-адресов**, пока пул не опустеет; настоящие клиенты ничего не получают (а чужой сервер может занять их место).

Защита:

    /ip dhcp-server alert add interface=bridgeLAN valid-server=D4:CA:6D:00:00:01 on-alert=":log warning rogue"
    /interface bridge set bridgeLAN dhcp-snooping=yes
    /interface bridge port set [find interface=ether2] trusted=yes

- **DHCP alert** пишет в лог (и может запустить скрипт), когда отвечает DHCP-сервер, отличный от правильного.
- **DHCP snooping** на бридже пропускает DHCP offer только через **доверенные (trusted)** порты (аплинк к настоящему серверу).

### Атаки на STP и BPDU guard

Устройство, отправляющее **BPDU** с лучшим приоритетом, может стать **корневым мостом** и изменить всю топологию. На портах к конечным пользователям задайте:

    /interface bridge port set [find interface=ether5] edge=yes bpdu-guard=yes

**BPDU guard** отключает порт, когда на него приходит BPDU.

# Lesson: Сканирование портов и перебор паролей

### Сканирование портов

Сканер (например, **nmap**) пробует много портов, чтобы найти открытые сервисы. Само сканирование не атака, но почти всегда это первый шаг атаки.

RouterOS обнаруживает сканирование с помощью **PSD** (port scan detection): `psd=WeightThreshold,DelayThreshold,LowPortWeight,HighPortWeight`.

    /ip firewall filter
    add chain=input protocol=tcp psd=21,3s,3,1 action=add-src-to-address-list \
        address-list=port_scanners address-list-timeout=2w comment="detect scan"
    /ip firewall raw
    add chain=prerouting src-address-list=port_scanners action=drop

Как считает PSD, пошагово, для `psd=21,3s,3,1`:

1. Каждый новый TCP-порт, который источник пробует в течение **3 с** после предыдущего, добавляет вес.
2. Порт **ниже 1024** добавляет **3**, порт выше добавляет **1**.
3. Когда сумма достигает **21**, правило срабатывает: например, 7 известных портов или 21 высокий порт.
4. Источник попадает в `port_scanners` на 2 недели, и RAW отбрасывает все его пакеты.

### Перебор паролей (brute force)

Атакующий пробует много паролей для SSH, Winbox, FTP... Сильные пароли помогают, но попытки тоже хочется остановить. Классический метод RouterOS использует **поэтапные списки адресов**:

    /ip firewall filter
    add chain=input protocol=tcp dst-port=22 src-address-list=ssh_blacklist action=drop
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage3 \
        action=add-src-to-address-list address-list=ssh_blacklist address-list-timeout=10d
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage2 \
        action=add-src-to-address-list address-list=ssh_stage3 address-list-timeout=1m
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage1 \
        action=add-src-to-address-list address-list=ssh_stage2 address-list-timeout=1m
    add chain=input protocol=tcp dst-port=22 connection-state=new \
        action=add-src-to-address-list address-list=ssh_stage1 address-list-timeout=1m

Проследим за одним атакующим, соединение за соединением (всё в пределах минуты):

| Попытка | Списки до | Что происходит |
|---|---|---|
| 1 | нет | Добавлен в stage1, соединение разрешено |
| 2 | stage1 | Добавлен в stage2, разрешено |
| 3 | stage1, 2 | Добавлен в stage3, разрешено |
| 4 | stage1, 2, 3 | Добавлен в **blacklist**, ещё разрешено |
| **5** | blacklist | **Отброшено** первым правилом, на 10 дней |

> **Почему порядок «сначала stage3, в конце stage1»?** `add-src-to-address-list` **не** останавливает обработку. Если бы stage1 стоял первым, тот же пакет попал бы в stage1, затем совпал бы со stage2, stage3 и blacklist, всё сразу. Обратный порядок заставляет каждый пакет подниматься только на одну ступень.

Администратор, который входит один или два раза, никогда не попадает в blacklist, а записи этапов истекают через минуту.

# Lesson: Отказ в обслуживании и подмена адресов

### DoS и DDoS

- **DoS** (Denial of Service, отказ в обслуживании): один источник перегружает сервис или канал.
- **DDoS** (распределённый DoS): трафик идёт **из множества источников** (часто ботнет). Блокировка одного адреса не помогает.

Распространённые виды:

| Атака | Как работает | Чем поможет RouterOS |
|---|---|---|
| **SYN flood** | Много TCP SYN, сервер держит полуоткрытые соединения, пока не кончатся таблица и CPU | `/ip settings set tcp-syncookies=yes`, отбрасывание известных источников в RAW |
| **Amplification (усиление)** | Маленькие поддельные запросы к открытым DNS/NTP/memcached серверам; большие ответы уходят жертве | Не быть открытым резолвером; отбрасывать поддельные источники |
| **Исчерпание соединений** | Один источник открывает тысячи соединений | `connection-limit=100,32` + список адресов |
| **Объёмная атака** | Канал просто заполнен | Помочь может только провайдер выше по течению |

**SYN cookies** позволяют маршрутизатору отвечать на SYN, не храня состояние полуоткрытых соединений: состояние закодировано в sequence number.

Пример правила ограничения соединений (на один адрес источника `/32`):

    /ip firewall filter add chain=input protocol=tcp connection-limit=100,32 \
        action=add-src-to-address-list address-list=too_many address-list-timeout=1h

### Подмена адреса и rp-filter

**Reverse path filtering** проверяет адрес источника каждого пакета: отправил бы маршрутизатор ответ этому источнику через **тот же** интерфейс?

    /ip settings set rp-filter=strict

- **strict**: пакет должен прийти с лучшего интерфейса в сторону источника.
- **loose**: источник должен быть достижим через любой интерфейс.

Поддельные пакеты, которые выдают себя за вашу LAN, но приходят с WAN, отбрасываются.

# Lesson: Обнаружение соседей, флуд и ограничение скорости

> Этот урок идёт по слайдам курса, глава 3 «Attacks, mechanisms and services».

### Протоколы обнаружения выдают вас

Прежде чем что-то сканировать, атакующий слушает. Три протокола объявляют устройство соседям, и ни один из них не аутентифицирован:

| Протокол | Кто говорит | Что раскрывает |
|---|---|---|
| **MNDP** (MikroTik Neighbor Discovery Protocol) | RouterOS, SwOS | Identity, версия RouterOS, модель платы, имя интерфейса, MAC, IP |
| **CDP** (Cisco Discovery Protocol) | Cisco, и RouterOS для совместимости | Идентификатор устройства, платформа, порт, версия ПО |
| **LLDP** (Link Layer Discovery Protocol) | Почти всё оборудование, IEEE 802.1AB | Имя системы, описание, порт, возможности, адрес управления |

RouterOS по умолчанию отвечает на все три. На WAN-порту это значит, что номер вашей версии опубликован для всех в сегменте, а именно по версии атакующий выбирает эксплойт.

Ограничьте обнаружение теми интерфейсами, где оно действительно нужно:

    /ip neighbor discovery-settings set discover-interface-list=LAN
    /ip neighbor print

Тот самый список интерфейсов `LAN` из прошлого модуля здесь и работает. Слайды связывают это с двумя атаками уровня соседей:

- **Флуд MNDP/CDP/LLDP**: тысячи поддельных объявлений в секунду. Каждое это маленький пакет, который CPU обязан разобрать, а таблицы соседей переполняются. Лечится не фильтрацией, а тем, чтобы не слушать: `discover-interface-list=none` на недоверенных портах.
- **Сбор информации**: достаточно одного правдоподобного объявления, чтобы прочитать вашу версию. Никакое ограничение скорости здесь не поможет, помогает только выключение обнаружения.

> **Не забудьте про бридж.** На бридже обнаружение следует за интерфейсом бриджа, а не за физическим портом. Если `bridge1` в списке `LAN`, то слышать и отвечать может любой порт этого бриджа.

### UDP-флуд и усиление

У UDP нет рукопожатия, поэтому отправителю не нужно доказывать, что он существует. Отсюда и любовь к нему в объёмных атаках:

- **Простой UDP-флуд**: пакеты на случайные порты. Каждый заставляет маршрутизатор сгенерировать ответ ICMP port unreachable, то есть атака обходится вам вдвойне.
- **Усиление (amplification)**: маленький запрос с подменённым источником к сервису, который отвечает намного большим объёмом. Классика это DNS, NTP, SNMP и memcached. 60-байтный запрос DNS может дать ответ в 3000 байт, то есть пятидесятикратное усиление, и ответ уходит жертве, а не атакующему.

Ответы RouterOS, по убыванию полезности:

    /ip firewall raw
    add chain=prerouting action=drop protocol=udp dst-port=53 in-interface-list=WAN comment="no DNS from WAN"

    /ip dns set allow-remote-requests=no

    /ip firewall filter
    add chain=input action=accept protocol=udp dst-port=53 src-address-list=trusted
    add chain=input action=drop protocol=udp dst-port=53

Первое правило самое важное: если ваш маршрутизатор не публичный резолвер, он вообще не должен отвечать на DNS из интернета. Открытый резолвер это не только ваша проблема, это оружие, направленное на кого-то другого.

### Ping-флуд и атака smurf

**Ping-флуд** это просто больше ICMP echo request, чем цель способна обработать. **Атака smurf** это усиленный вариант, и её стоит разобрать по шагам:

1. Атакующий отправляет ICMP echo request.
2. **Адрес источника подменён** на адрес жертвы.
3. **Получатель это широковещательный адрес**, например 192.168.88.255.
4. Отвечают все хосты этой подсети.
5. Все ответы приходят жертве, которая ничего не отправляла.

Один пакет внутрь, сотня пакетов наружу, и адрес атакующего нигде не появляется. Защита эшелонированная:

    /ip firewall raw
    add chain=prerouting action=drop dst-address-type=broadcast protocol=icmp in-interface-list=WAN

    /ip settings set rp-filter=strict

- Не маршрутизируйте ICMP на широковещательные адреса снаружи.
- `rp-filter=strict` отбрасывает пакет, адрес источника которого не мог законно прийти на этот интерфейс, и это убивает почти всю подмену на входе.
- Остальное ограничьте по скорости, см. ниже.

### Ограничение скорости: limit и burst

Ограничение скорости это способ что-то разрешить и при этом выжить при флуде этим же. В RouterOS это пишется как `limit=количество/время,burst`:

    /ip firewall filter
    add chain=input protocol=icmp action=accept limit=50/5s,10 comment="50 пингов за 5с, burst 10"
    add chain=input protocol=icmp action=drop comment="остальное"

Читайте два числа отдельно:

- **`50/5s`** это постоянная скорость: «ведро» наполняется на пятьдесят пакетов каждые пять секунд.
- **`10`** это burst: сколько ведро может хранить, когда оно полное, так что короткий всплеск в десять пакетов проходит без потерь.

Следующим правилом обязательно должен быть `drop`, потому что `limit` совпадает только *пока лимит не исчерпан*. Как только ведро пусто, правило перестаёт совпадать, и пакет падает в следующее правило. Поэтому пара всегда «accept, затем drop».

### Цепочка от SYN-атаки

**SYN-флуд** отправляет первый пакет рукопожатия TCP и никогда третий. Каждое полуоткрытое соединение держит состояние, и таблица переполняется. Слайды строят под это отдельную цепочку:

    /ip firewall filter
    add chain=forward protocol=tcp tcp-flags=syn connection-state=new action=jump jump-target=SYN-Protect
    add chain=SYN-Protect protocol=tcp tcp-flags=syn limit=400,burst=400 connection-state=new action=return
    add chain=SYN-Protect protocol=tcp tcp-flags=syn connection-state=new action=drop

Почему `return`, а не `accept`: если пакет в пределах лимита, он возвращается в `forward` и продолжает проходить остальную политику, то есть ограничение скорости случайно не обходит ваши другие правила. Внутри цепочки отбрасываются только пакеты сверх лимита.

Есть и встроенный помощник:

    /ip settings set tcp-syncookies=yes

**SYN cookies** позволяют маршрутизатору ответить на рукопожатие, не выделяя состояние, и создать соединение только когда третий пакет докажет, что клиент настоящий. Включайте: стоит немного CPU на рукопожатие и спасает всю таблицу.

### Скрытые сканирования и как их ловить

Сканеру не нужно завершать рукопожатие, чтобы узнать, открыт ли порт. Слайды перечисляют комбинации флагов, которые использует `nmap`, и каждая из них это невозможный пакет, который настоящий стек никогда не отправит:

| Сканирование | Флаги | Бывает в норме? |
|---|---|---|
| **FIN scan** | только `fin`, без `ack` | Нет, FIN всегда идёт после сессии |
| **NULL scan** | флагов нет вообще | Нет |
| **XMAS scan** | `fin,psh,urg` вместе | Нет |
| **SYN+FIN** | `syn,fin` | Противоречие: открыть и закрыть одновременно |
| **SYN+RST** | `syn,rst` | Противоречие |
| **FIN+RST** | `fin,rst` | Противоречие |

Раз они невозможны, их можно отбрасывать без риска ложных срабатываний:

    /ip firewall filter
    add chain=input protocol=tcp tcp-flags=fin,!ack action=drop comment="FIN scan"
    add chain=input protocol=tcp tcp-flags=!fin,!syn,!rst,!psh,!ack,!urg action=drop comment="NULL scan"
    add chain=input protocol=tcp tcp-flags=fin,psh,urg action=drop comment="XMAS scan"
    add chain=input protocol=tcp tcp-flags=fin,syn action=drop
    add chain=input protocol=tcp tcp-flags=syn,rst action=drop
    add chain=input protocol=tcp tcp-flags=fin,rst action=drop

Синтаксис достоин отдельной строки: внутри `tcp-flags` имя означает *флаг установлен*, а `!имя` означает *флаг снят*. То есть `fin,!ack` это «FIN установлен и ACK снят», а в правиле NULL-сканирования все шесть флагов перечислены как снятые.

Для connect-сканирований, которые используют нормальные флаги, правильный инструмент это матчер PSD и приём со списком адресов из урока про сканирование портов.

### Лаба со слайдов

> **Лаба:** *Выключите обнаружение соседей в сторону WAN, добавьте ограничение скорости для ICMP и отбросьте невозможные комбинации флагов TCP.*

1. `/ip neighbor discovery-settings set discover-interface-list=LAN`, и проверьте через `/ip neighbor print` с маршрутизатора соседа, что вы исчезли.
2. Добавьте accept с limit для ICMP и drop после него. Проверьте через `ping -f` или флудер и посмотрите на счётчики.
3. Добавьте шесть правил против скрытых сканирований. Запустите FIN- или XMAS-сканирование с соседнего маршрутизатора и убедитесь, что счётчики растут, а сканирование ничего не показывает.
4. Включите `tcp-syncookies` и `rp-filter=strict`, затем проверьте, что обычный трафик по-прежнему работает.
