# Lesson: Атаки второго уровня

Атаки второго уровня идут **изнутри** LAN: гостевой ноутбук, заражённый ПК, устройство, которое кто-то подключил в свободный порт. IP-файрвол маршрутизатора большинство из них не видит, поэтому нужны настройки коммутатора и бриджа.

### MAC flooding

Коммутатор запоминает, какой MAC-адрес находится за каким портом, и хранит это в **таблице MAC (host table)**. Размер таблицы ограничен.

Как работает атака, пошагово:

1. Атакующий отправляет тысячи кадров со **случайными MAC-адресами источника**.
2. Таблица заполняется фальшивыми записями.
3. Настоящие хосты больше не запоминаются, и коммутатор **рассылает** их кадры во все порты, как хаб.
4. Атакующий перехватывает трафик, который ему не предназначался.

Защита: ограничьте число запоминаемых MAC на порт (port security на коммутаторах CRS), используйте 802.1X и не оставляйте включёнными свободные порты в общественных местах.

### ARP-спуфинг

ARP сопоставляет IP-адреса и MAC-адреса и не имеет аутентификации. Атакующий отправляет поддельные ARP-ответы: *«192.168.88.1 находится по МОЕМУ MAC»*. Жертвы отправляют трафик для шлюза атакующему (**man-in-the-middle**, «человек посередине»).

Защита RouterOS на интерфейсе LAN:

    /interface bridge set bridgeLAN arp=reply-only
    /ip dhcp-server set dhcp1 add-arp=yes

- **arp=reply-only**: маршрутизатор не изучает ARP-записи из сети, использует только статические.
- **add-arp=yes**: DHCP-сервер добавляет статическую ARP-запись для каждой аренды, поэтому DHCP-клиенты продолжают работать.

Маршрутизатор игнорирует поддельные ARP-ответы о хостах. (Клиентов всё ещё можно обмануть насчёт шлюза; на управляемых коммутаторах используйте DHCP snooping с ARP inspection.)

### Чужой DHCP и DHCP starvation

- **Чужой DHCP-сервер (rogue DHCP)**: кто-то подключил домашний роутер или неправильно настроил ПК. Клиенты получают **неверный шлюз или DNS**, случайно или чтобы перенаправить их.
- **DHCP starvation (истощение)**: атакующий запрашивает аренды с **множеством поддельных MAC-адресов**, пока пул не опустеет; настоящие клиенты ничего не получают (а чужой сервер может занять их место).

Защита:

    /ip dhcp-server alert add interface=bridgeLAN valid-server=D4:CA:6D:00:00:01 on-alert=":log warning rogue"
    /interface bridge set bridgeLAN dhcp-snooping=yes
    /interface bridge port set [find interface=ether2] trusted=yes

- **DHCP alert** пишет в лог (и может запустить скрипт), когда отвечает DHCP-сервер, отличный от правильного.
- **DHCP snooping** на бридже пропускает DHCP offer только через **доверенные (trusted)** порты (аплинк к настоящему серверу).

### Атаки на STP и BPDU guard

Устройство, отправляющее **BPDU** с лучшим приоритетом, может стать **корневым мостом** и изменить всю топологию. На портах к конечным пользователям задайте:

    /interface bridge port set [find interface=ether5] edge=yes bpdu-guard=yes

**BPDU guard** отключает порт, когда на него приходит BPDU.

# Lesson: Сканирование портов и перебор паролей

### Сканирование портов

Сканер (например, **nmap**) пробует много портов, чтобы найти открытые сервисы. Само сканирование не атака, но почти всегда это первый шаг атаки.

RouterOS обнаруживает сканирование с помощью **PSD** (port scan detection): `psd=WeightThreshold,DelayThreshold,LowPortWeight,HighPortWeight`.

    /ip firewall filter
    add chain=input protocol=tcp psd=21,3s,3,1 action=add-src-to-address-list \
        address-list=port_scanners address-list-timeout=2w comment="detect scan"
    /ip firewall raw
    add chain=prerouting src-address-list=port_scanners action=drop

Как считает PSD, пошагово, для `psd=21,3s,3,1`:

1. Каждый новый TCP-порт, который источник пробует в течение **3 с** после предыдущего, добавляет вес.
2. Порт **ниже 1024** добавляет **3**, порт выше добавляет **1**.
3. Когда сумма достигает **21**, правило срабатывает: например, 7 известных портов или 21 высокий порт.
4. Источник попадает в `port_scanners` на 2 недели, и RAW отбрасывает все его пакеты.

### Перебор паролей (brute force)

Атакующий пробует много паролей для SSH, Winbox, FTP... Сильные пароли помогают, но попытки тоже хочется остановить. Классический метод RouterOS использует **поэтапные списки адресов**:

    /ip firewall filter
    add chain=input protocol=tcp dst-port=22 src-address-list=ssh_blacklist action=drop
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage3 \
        action=add-src-to-address-list address-list=ssh_blacklist address-list-timeout=10d
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage2 \
        action=add-src-to-address-list address-list=ssh_stage3 address-list-timeout=1m
    add chain=input protocol=tcp dst-port=22 connection-state=new src-address-list=ssh_stage1 \
        action=add-src-to-address-list address-list=ssh_stage2 address-list-timeout=1m
    add chain=input protocol=tcp dst-port=22 connection-state=new \
        action=add-src-to-address-list address-list=ssh_stage1 address-list-timeout=1m

Проследим за одним атакующим, соединение за соединением (всё в пределах минуты):

| Попытка | Списки до | Что происходит |
|---|---|---|
| 1 | нет | Добавлен в stage1, соединение разрешено |
| 2 | stage1 | Добавлен в stage2, разрешено |
| 3 | stage1, 2 | Добавлен в stage3, разрешено |
| 4 | stage1, 2, 3 | Добавлен в **blacklist**, ещё разрешено |
| **5** | blacklist | **Отброшено** первым правилом, на 10 дней |

> **Почему порядок «сначала stage3, в конце stage1»?** `add-src-to-address-list` **не** останавливает обработку. Если бы stage1 стоял первым, тот же пакет попал бы в stage1, затем совпал бы со stage2, stage3 и blacklist, всё сразу. Обратный порядок заставляет каждый пакет подниматься только на одну ступень.

Администратор, который входит один или два раза, никогда не попадает в blacklist, а записи этапов истекают через минуту.

# Lesson: Отказ в обслуживании и подмена адресов

### DoS и DDoS

- **DoS** (Denial of Service, отказ в обслуживании): один источник перегружает сервис или канал.
- **DDoS** (распределённый DoS): трафик идёт **из множества источников** (часто ботнет). Блокировка одного адреса не помогает.

Распространённые виды:

| Атака | Как работает | Чем поможет RouterOS |
|---|---|---|
| **SYN flood** | Много TCP SYN, сервер держит полуоткрытые соединения, пока не кончатся таблица и CPU | `/ip settings set tcp-syncookies=yes`, отбрасывание известных источников в RAW |
| **Amplification (усиление)** | Маленькие поддельные запросы к открытым DNS/NTP/memcached серверам; большие ответы уходят жертве | Не быть открытым резолвером; отбрасывать поддельные источники |
| **Исчерпание соединений** | Один источник открывает тысячи соединений | `connection-limit=100,32` + список адресов |
| **Объёмная атака** | Канал просто заполнен | Помочь может только провайдер выше по течению |

**SYN cookies** позволяют маршрутизатору отвечать на SYN, не храня состояние полуоткрытых соединений: состояние закодировано в sequence number.

Пример правила ограничения соединений (на один адрес источника `/32`):

    /ip firewall filter add chain=input protocol=tcp connection-limit=100,32 \
        action=add-src-to-address-list address-list=too_many address-list-timeout=1h

### Подмена адреса и rp-filter

**Reverse path filtering** проверяет адрес источника каждого пакета: отправил бы маршрутизатор ответ этому источнику через **тот же** интерфейс?

    /ip settings set rp-filter=strict

- **strict**: пакет должен прийти с лучшего интерфейса в сторону источника.
- **loose**: источник должен быть достижим через любой интерфейс.

Поддельные пакеты, которые выдают себя за вашу LAN, но приходят с WAN, отбрасываются.
