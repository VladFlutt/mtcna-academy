# Lesson: Что QoS может и чего не может

**Качество обслуживания** делит ограниченный канал между трафиком, которому нужно разное обращение: голосу нужна низкая задержка, веб-странице быстрые ответы, резервной копии только чтобы она когда-нибудь закончилась. QoS на маршрутизаторе может:

- **ограничивать** скорость пользователя, сервиса или направления;
- **гарантировать** минимальную скорость важному трафику;
- **давать приоритет**: отдавать свободную полосу сначала важному трафику;
- **делить честно** между пользователями.

Он не создаёт полосу и управляет только тем, что **выходит** из маршрутизатора. Загрузки ограничиваются на выходе в LAN, уже после прохода через канал в Интернет; отправители TCP затем замедляются, потому что подтверждения приходят медленнее.

## Шейпер и планировщик

- **Шейпер** без очереди отбрасывает каждый пакет сверх скорости: нет лишней задержки, но много потерь.
- **Планировщик** с бесконечной очередью никогда не отбрасывает: пакеты ждут, и задержка растёт без предела.

Реальные очереди посередине: ограниченная очередь сглаживает всплески (некоторая задержка) и отбрасывает, когда заполнена. Большая очередь под нагрузкой даёт большие задержки (**bufferbloat**); маленькая держит задержку низкой, но теряет больше.

## CIR и MIR

| Термин | RouterOS | Смысл |
|---|---|---|
| CIR, committed information rate | **limit-at** | гарантированная скорость, выдаётся в любом случае |
| MIR, maximum information rate | **max-limit** | максимум, который очередь может получить, если у родителя осталась полоса |

Все очереди RouterOS (простые очереди и queue tree) реализованы через **HTB**, иерархическое ведро токенов, которое работает с этими двумя скоростями.

# Lesson: Типы очередей

**Тип очереди** определяет, как пакеты ждут внутри одной очереди: какой уходит следующим и какой отбрасывается.

| Kind | Поведение |
|---|---|
| **pfifo / bfifo** | первым пришёл, первым ушёл; размер очереди в пакетах (pfifo-limit, по умолчанию 50) или байтах (bfifo-limit) |
| **mq-pfifo** | pfifo с несколькими аппаратными очередями, для многоочередных интерфейсов |
| **RED** | random early detection: когда средняя длина очереди превышает **min-threshold**, пакеты отбрасываются случайно с растущей вероятностью, а выше **max-threshold** отбрасываются все. Отправители TCP замедляются заранее, а не все одновременно |
| **SFQ** | stochastic fairness queuing: потоки раскладываются хэшем по 1024 подочередям и обслуживаются по кругу, по `sfq-allot` (1514) байт; хэш меняется каждые `sfq-perturb` (5) секунд. Честно между потоками, но не между пользователями |
| **PCQ** | per connection queue: подпотоки по классификатору (адрес или порт источника или назначения), у каждого `pcq-rate`; честно между пользователями |
| **fq-codel, codel, cake** | RouterOS 7: активное управление очередью, которое держит задержку низкой под нагрузкой. CAKE ещё и ограничивает скорость, честно делит по хостам и потокам и учитывает накладные расходы DSL или DOCSIS |

У интерфейсов есть тип очереди по умолчанию (`/queue interface`): на Ethernet обычно `only-hardware-queue` или `multi-queue-ethernet-default`, для беспроводных свой. Дочерние очереди дерева используют `default-small` (pfifo 10), если не задать другой `queue=`.

Деталь RouterOS 7: параметры CAKE и fq_codel (target, interval, bandwidth, overhead) различаются между версиями; проверьте `/queue type print detail` на своём устройстве, прежде чем копировать значения из старых руководств.

# Lesson: PCQ и burst

## PCQ

Одна очередь PCQ заменяет сотни очередей на пользователей:

    /queue type add name=pcq-down kind=pcq pcq-classifier=dst-address pcq-rate=0
    /queue type add name=pcq-up kind=pcq pcq-classifier=src-address pcq-rate=0
    /queue simple add name=lan target=192.168.33.0/24 max-limit=10M/10M queue=pcq-up/pcq-down

- **Классификатор**: загрузка адресована пользователю, поэтому `dst-address`; отдача идёт от пользователя, поэтому `src-address`.
- **pcq-rate = 0**: нет ограничения на подпоток; max-limit очереди делится **поровну** между активными пользователями.
- **pcq-rate > 0**: каждый подпоток получает **min(pcq-rate, max-limit / пользователи)**.
- `pcq-limit` (50 пакетов на подпоток) и `pcq-total-limit` (2000) ограничивают память; `pcq-dst-address-mask` группирует пользователей (например, /24 на клиента).

| max-limit 512k | pcq-rate 0 | pcq-rate 128k |
|---|---|---|
| 1 пользователь | 512k | 128k |
| 2 пользователя | по 256k | по 128k (256k не используются) |
| 4 пользователя | по 128k | по 128k |
| 7 пользователей | по ~73k | по ~73k |

Неактивные пользователи ничего не получают и ничего не занимают: доля растёт, как только кто-то останавливается. Проверьте числа в симуляторе **PCQ**.

## Burst

Burst позволяет очереди ненадолго работать выше max-limit, чтобы короткие загрузки (веб-страницы) были быстрыми, а длинные ограничивались.

| Параметр | Смысл |
|---|---|
| burst-limit | скорость во время burst (выше max-limit) |
| burst-threshold | burst разрешён, пока **средняя** скорость ниже этого значения (ниже max-limit) |
| burst-time | период, за который считается среднее (в 16 шагов) |

Пример со слайдов: max-limit 256k, burst-limit 512k, burst-threshold 192k, burst-time 8 с. Из простоя пользователь получает 512k. Среднее за последние 8 секунд растёт на 64k в секунду: 64, 128, 192. На 3 секунде оно достигает порога, и очередь возвращается к 256k. Новый burst разрешён только после того, как пользователь помолчит достаточно, чтобы среднее упало ниже 192k.

![Burst: 512k, пока среднее за 8 секунд не достигнет порога 192k, затем max-limit](/img/mtctce/burst.svg)

Длительность burst из простоя ≈ burst-threshold × burst-time / burst-limit. Если burst-threshold не ниже max-limit, пользователь на max-limit никогда его не достигнет и будет в burst всегда. Начиная с RouterOS 5 PCQ тоже умеет burst на подпоток (`pcq-burst-rate`, `pcq-burst-threshold`, `pcq-burst-time`). Поэкспериментируйте в симуляторе **burst**.

# Lesson: Простые очереди

    /queue simple add name=user20 target=192.168.33.20/32 max-limit=1M/2M
    /queue simple add name=lan target=192.168.33.0/24 max-limit=10M/10M queue=pcq-up/pcq-down

- **target**: адреса, подсети или интерфейс; очередь применяется к трафику к ним и от них. `dst=` сужает её до назначения (например, только трафик к 22.1.1.1).
- Два значения `upload/download`: upload это трафик **от** цели, download трафик **к** ней. То же для limit-at, burst-limit, burst-threshold, burst-time и queue.
- Очереди проверяются **сверху вниз**; пакет обрабатывается **первой** совпавшей очередью. Ставьте отдельные хосты выше целых подсетей.
- `packet-marks=` ограничивает очередь маркированными пакетами; `parent=` строит иерархию простых очередей; `time=` делает очередь активной только в определённое время и дни.
- `priority` действует между простыми очередями с одним родителем, как в queue tree.

Простые очереди легко читать, и они хороши для ограничений по хостам или клиентам. На длинных списках они нагружают CPU, потому что каждый пакет сравнивается с очередями по порядку, и работают сразу в обе стороны. Для приоритетов между классами трафика используйте queue tree.

Лаба курса: LAN получает PCQ по 256k на пользователя, веб-трафик по 512k на пользователя, а тесты скорости к 22.1.1.1 burst 700k при max-limit 300k. Лаба **PCQ и burst** здесь делает похожую работу.

# Lesson: HTB подробно

HTB выстраивает очереди в дерево:

- у **листьев** нет детей; пакеты ждут только в листьях, у которых есть метки пакетов и приоритеты;
- у **внутренних** очередей есть дети; они только распределяют полосу.

Правила:

- сумма limit-at детей не должна превышать limit-at родителя, а max-limit ребёнка не должен превышать max-limit родителя;
- **priority** (1 высший, 8 низший) используется только **листьями** и только для полосы сверх limit-at; внутренние очереди его игнорируют;
- очередь без max-limit ограничена родителем.

## Как HTB делит полосу

1. **Сначала CIR.** Каждый лист получает свой limit-at, столько, сколько ему из этого нужно. Если limit-at листьев вместе больше, чем может дать родитель, они урезаются пропорционально.
2. **Гарантии внутренних очередей.** Внутренняя очередь, у которой limit-at больше, чем взяли её листья, оставляет разницу **своим листьям**, по их приоритету.
3. **Остаток** уходит листьям по приоритету, начиная с высшего, каждому до его max-limit (и max-limit его родителей). Листья с одинаковым приоритетом делят поровну.

Примеры со слайдов (все хотят максимум):

| Дерево | Результат |
|---|---|
| A max 5M; B limit-at 2M max 4M priority 1; C limit-at 2M max 4M priority 8 | B 3M, C 2M: оба получают по 2M, свободный 1M уходит B |
| A max 8M; B 2M/4M p1; C 4M/6M с C1 2M/3M p4, C2 2M/3M p8 | B 4M, C1 2M, C2 2M: у B лучший приоритет среди листьев |
| то же с B p2 и C p1 | без изменений: C внутренняя очередь, её приоритет игнорируется |
| A max 8M; B 2M/4M (B1, B2 1M/2M, p5, p6); C 3M/6M (C1, C2, C3 1M/2M, p2, p3, p4) | B1 1, B2 1, C1 2, C2 2, C3 2: остаток 3M по приоритету |
| то же с B limit-at 4M | B1 2, B2 2, C1 2, C2 1, C3 1: B гарантирует 4M своим листьям |

Дерево из лабы курса на канале 30M:

![Дерево лабы и то, что получает каждый лист при полной нагрузке](/img/mtctce/htb-lab.svg)

По шагам: CIR листьев 7 + 2 + 2 + 2 + 3 = 16M. У B limit-at 15M, а его листья взяли только 9M, поэтому B даёт своим листьям ещё 6M по приоритету: B1 (priority 7) получает 3M до своего максимума 10M, B2 оставшиеся 3M. Итого 22M. Последние 8M уходят листу с лучшим приоритетом, C1 (priority 2), до его 10M. Результат: B1 10M, B2 5M, C1 10M, C2 2M, C3 3M.

Если C2 остановится, а B1 нужно только 3M, свободная полоса перераспределяется: B2 получает всю гарантию B (12M), C1 поднимается до 10M, а C3 забирает остаток. Повторите примеры в **распределении HTB**.

# Lesson: Деревья очередей

    /queue tree add name=down parent=bridgeLAN max-limit=30M
    /queue tree add name=voip parent=down packet-mark=voip limit-at=2M max-limit=5M priority=1
    /queue tree add name=web parent=down packet-mark=web limit-at=5M max-limit=30M priority=3
    /queue tree add name=other parent=down packet-mark=no-mark limit-at=1M max-limit=30M priority=8

- **parent=<interface>**: дерево ограничивает пакеты, выходящие через этот интерфейс: загрузку на LAN-интерфейсе, отдачу на WAN-интерфейсе.
- **parent=global**: дерево видит оба направления на всех интерфейсах; метки пакетов должны разделять отдачу и загрузку.
- Лист queue tree выбирается только по **метке пакета**; `packet-mark=no-mark` ловит немаркированные пакеты.
- Queue tree однонаправленные и требуют mangle для всего, но хорошо масштабируются и дают полный контроль над приоритетами.
- Пакеты FastTrack для queue tree невидимы.

Winbox окрашивает очередь по загрузке: зелёный до 50% от max-limit, жёлтый 51-75%, красный выше 75%.

## План для филиала из курса

Филиал с 6 рабочими местами, 10M на загрузку и 5M на отдачу, VoIP до головного офиса через туннель, RDP/ICA к терминальным серверам, удалённый файловый сервер и Интернет:

| Класс | Метка | limit-at | Приоритет |
|---|---|---|---|
| VoIP | voip (DSCP 46) | достаточно для всех звонков | 1 |
| RDP / ICA | rdp | 1-2M | 2 |
| файловый сервер | files | 1M гарантировано | 5 |
| Интернет | no-mark | 2M гарантировано | 8 (низший) |

1. Маркируйте соединения по классам в prerouting, затем пакеты по метке соединения.
2. Одно дерево на направление, с реальной скоростью линии (чуть ниже неё, чтобы очередь формировалась на маршрутизаторе, а не у провайдера).
3. limit-at для каждого класса, max-limit на скорость линии, чтобы классы могли занимать полосу.

Лаба **дерево HTB** строит дерево из курса на симулированном маршрутизаторе и проверяет, что распределение в точности такое, как выше.
