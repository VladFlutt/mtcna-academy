# Lesson: Таблицы маршрутизации

Обычная маршрутизация смотрит только на адрес **назначения**. Иногда решение должно зависеть от чего-то другого:

- компьютер бухгалтера должен ходить через второго провайдера;
- VoIP идёт по оптике, всё остальное через LTE;
- на соединение, пришедшее через ISP2, нужно отвечать через ISP2;
- гости и сотрудники используют разные каналы.

**Маршрутизация по политикам** (policy based routing, PBR) решает это с помощью нескольких таблиц маршрутизации. Каждая таблица является полным набором маршрутов; политика решает, в какой таблице искать маршрут для пакета.

## Создание таблицы (RouterOS 7)

    /routing table add name=isp2 fib
    /ip route add gateway=172.16.2.1 routing-table=isp2

- `fib` означает, что таблица передаётся в механизм пересылки. Таблица без `fib` существует только для протоколов маршрутизации и не может использоваться для пересылки пакетов.
- Таблица **main** существует всегда. Маршруты без `routing-table=` попадают в неё.
- В таблице нужны только те маршруты, которые должны отличаться. Здесь в isp2 лежит только маршрут по умолчанию.

Показать одну таблицу:

    /ip route print where routing-table=isp2

> **RouterOS 6:** объектов таблиц не было. Маршрут получал `routing-mark=isp2`, и имя метки было таблицей. Та же идея, другой синтаксис: `/ip route add gateway=172.16.2.1 routing-mark=isp2`.

## Два способа выбрать таблицу

1. **Правила маршрутизации** (`/routing rule`): проверяют адрес источника и назначения, входящий интерфейс или routing mark и говорят, какую таблицу использовать.
2. **Mangle** (`action=mark-routing`): помечает пакеты по любому признаку firewall (порты, протоколы, address list, метки соединений), и метка выбирает таблицу.

![Метки mangle и правила маршрутизации решают, в какой таблице ищется маршрут для пакета](/img/mtcre/pbr-flow.svg)

Используйте правила, когда достаточно адресов источника или назначения; они дешевле и понятнее. Используйте mangle, когда нужны порты, протоколы или состояние соединения. Попробуйте оба способа в симуляторе **Путь через политики маршрутизации**.

# Lesson: Правила маршрутизации

    /routing rule add src-address=192.168.1.20/32 action=lookup table=isp2
    /routing rule add dst-address=10.0.0.0/8 action=lookup-only-in-table table=main
    /routing rule add src-address=172.16.2.2/32 action=lookup table=isp2

Правила проверяются **сверху вниз**; решает первое подходящее. Если не подошло ни одно, используется таблица main.

## Условия

| Условие | Пример |
|---|---|
| src-address | `src-address=192.168.1.0/24` |
| dst-address | `dst-address=10.0.0.0/8` |
| interface | `interface=ether5` (входящий интерфейс) |
| routing-mark | `routing-mark=isp2` (метка, поставленная mangle) |

## Действия

| Действие | Значение |
|---|---|
| lookup | искать в этой таблице; **если в ней нет подходящего активного маршрута, продолжить в main** |
| lookup-only-in-table | искать только в этой таблице; нет маршрута, значит пакет отбрасывается |
| drop | молча отбросить |
| unreachable | отбросить и отправить ICMP unreachable |

Разница между `lookup` и `lookup-only-in-table` есть разница между «предпочитать ISP2» и «только ISP2». С `lookup`, если кабель к ISP2 перерезан, маршрут по умолчанию в таблице isp2 становится неактивным, таблица пуста, и пакет уходит в main (ISP1). С `lookup-only-in-table` пользователь остаётся без сети, пока ISP2 не вернётся; это то, что нужно, когда трафик никогда не должен выходить через другого провайдера (например, VPN, который обязан идти по определённой линии).

## Порядок важен

Исключения ставьте первыми. Типичная схема:

1. трафик между вашими LAN → main (чтобы локальный трафик не уходил к провайдеру);
2. определённые пользователи или серверы → таблица их провайдера;
3. всё остальное → main (правило не нужно).

    /routing rule add dst-address=192.168.0.0/16 action=lookup-only-in-table table=main
    /routing rule add src-address=192.168.1.20/32 action=lookup table=isp2

> **RouterOS 6:** `/ip route rule add src-address=192.168.1.20/32 action=lookup table=isp2`. Те же условия и действия.

# Lesson: Mangle и метки маршрутизации

Mangle может поставить пакету routing mark в цепочке **prerouting** (трафик через маршрутизатор) или **output** (трафик от самого маршрутизатора). Решение о маршрутизации тогда сначала ищет в таблице с этим именем.

    /ip firewall mangle add chain=prerouting src-address=192.168.1.0/24 protocol=tcp dst-port=443 \
        dst-address-type=!local action=mark-routing new-routing-mark=isp2 passthrough=no

- `dst-address-type=!local` исключает из пометки трафик к самому маршрутизатору (DNS, Winbox).
- В RouterOS 7 routing mark должна быть именем существующей таблицы маршрутизации.
- Помеченный пакет ищется в этой таблице; если в ней нет подходящего маршрута, он уходит в main (как `action=lookup`).
- У пакета может быть только одна routing mark: более позднее правило перезаписывает метку более раннего, поэтому, когда решение принято, используйте `passthrough=no`.

## Сначала метим соединения, потом маршрутизируем

Помечать каждый пакет по множеству условий дорого и, что хуже, может разорвать одно соединение: первый пакет соединения подходит под `dst-port=443`, а последующие пакеты связанных потоков могут не подойти. Надёжная схема метит **соединение** один раз и выводит из него routing mark:

    /ip firewall mangle
    add chain=prerouting src-address=192.168.1.0/24 dst-port=443 protocol=tcp \
        connection-state=new action=mark-connection new-connection-mark=via-isp2
    add chain=prerouting connection-mark=via-isp2 in-interface=bridgeLAN \
        action=mark-routing new-routing-mark=isp2 passthrough=no

## FastTrack

Пакеты, прошедшие FastTrack, минуют mangle и поэтому никогда не получают routing mark. Если у вас стандартный firewall с правилом FastTrack, исключите из него помеченные соединения (добавьте `connection-mark=no-mark` в правило fasttrack), иначе PBR будет работать только для первых пакетов каждого соединения.

> **RouterOS 6:** те же правила mangle. Таблицей была просто routing mark маршрута.

# Lesson: Два провайдера: отвечать по той же линии

Маршрутизатор с двумя подключениями к Интернету, у каждого свой публичный адрес (172.16.1.2 от ISP1, 172.16.2.2 от ISP2), и маршрут по умолчанию через ISP1.

Кто-то в Интернете подключается к 172.16.2.2 (VPN, Winbox, проброс порта). Запрос приходит через ISP2. Маршрутизатор отвечает с адреса 172.16.2.2… и ищет маршрут по умолчанию в main, который указывает на ISP1. ISP1 получает пакет, адрес источника которого принадлежит сети ISP2. Аккуратный провайдер его отбрасывает (*reverse-path filtering*, BCP 38). Соединение никогда не работает, и в ваших логах ничего не объясняет почему.

## Решение 1: правило по адресу источника

Пакеты, которые маршрутизатор сам отправляет с 172.16.2.2, должны уходить через ISP2:

    /routing table add name=isp2 fib
    /ip route add gateway=172.16.2.1 routing-table=isp2
    /routing rule add src-address=172.16.2.2/32 action=lookup table=isp2

Это покрывает трафик к самому маршрутизатору и от него. Лаба **Маршрутизация по политикам с двумя провайдерами** проверяет именно это: WEB в Интернете должен пинговать 172.16.2.2.

## Решение 2: пробросы портов (метки соединений)

При пробросе порта на сервер в LAN ответ идёт с частного адреса сервера и транслируется обратно в 172.16.2.2 только после решения о маршрутизации. Правило по адресу источника его не видит, поэтому пометьте соединение по интерфейсу, через который оно пришло, и маршрутизируйте его ответы по этой метке:

    /ip firewall mangle
    add chain=prerouting in-interface=ether2 connection-state=new \
        action=mark-connection new-connection-mark=from-isp2
    add chain=prerouting in-interface=bridgeLAN connection-mark=from-isp2 \
        action=mark-routing new-routing-mark=isp2 passthrough=no
    add chain=output connection-mark=from-isp2 action=mark-routing new-routing-mark=isp2 passthrough=no

## NAT с двумя провайдерами

Masquerade отдельно на каждом WAN-интерфейсе:

    /ip firewall nat add chain=srcnat out-interface=ether1 action=masquerade
    /ip firewall nat add chain=srcnat out-interface=ether2 action=masquerade

Так как src-nat происходит после маршрутизации, пакет получает адрес того интерфейса, который выбрало решение о маршрутизации.

## Резервирование для политики

Если PC2 ходит через ISP2 по правилу `lookup` и кабель к ISP2 перерезан, таблица isp2 становится пустой, и PC2 уходит в main. Чтобы ловить и тихие отказы, поставьте `check-gateway=ping` на маршрут в таблице isp2. Последнее задание лабы перерезает кабель к ISP2 и проверяет, что PC2 всё равно выходит в Интернет.

## rp-filter на вашем маршрутизаторе

В RouterOS есть та же защита: `/ip settings set rp-filter=strict` отбрасывает пакеты, адрес источника которых не маршрутизировался бы обратно через интерфейс, на который они пришли. С двумя провайдерами и policy routing строгий режим может отбрасывать нормальный трафик; на маршрутизаторах с несколькими провайдерами используйте `loose` (источник должен быть достижим через любой интерфейс) или выключите его.
