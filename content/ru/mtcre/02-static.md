# Lesson: Статические маршруты, суммирование и blackhole

Статический маршрут является строкой, которую вы добавляете вручную: *чтобы попасть в эту сеть, отправляй пакеты на этот шлюз*.

    /ip route add dst-address=192.168.3.0/24 gateway=10.0.13.2
    /ip route add dst-address=0.0.0.0/0 gateway=172.16.1.1
    /ip route add gateway=172.16.1.1          (dst-address по умолчанию 0.0.0.0/0)

Статическая маршрутизация проста, предсказуема и не тратит ни CPU, ни полосу. Её слабость: сама по себе она ничего не меняет. Если канал отказал, маршрут остаётся, пока вы (или check-gateway, см. ниже) что-нибудь не сделаете.

## Маршрут по умолчанию, суммарный, хостовый

- **Маршрут по умолчанию** `0.0.0.0/0`: всё, что не покрыто более точным маршрутом. Типично для филиала с одним выходом наружу.
- **Суммарный маршрут**: один маршрут, покрывающий несколько сетей, например `192.168.0.0/22` для сетей с 192.168.0.0/24 по 192.168.3.0/24. Маршрутов меньше, но только если сети действительно находятся за одним шлюзом и пронумерованы так, что их можно суммировать.
- **Хостовый маршрут** `/32`: ровно один адрес. Используется для loopback-адресов, PPP-пиров и в рекурсивной маршрутизации, чтобы привязать хост мониторинга к одному провайдеру.

Из-за правила самого длинного префикса более точный маршрут всегда выигрывает у суммарного. Можно отправить 192.168.0.0/16 в одну сторону, а 192.168.5.0/24 всё равно в другую.

## Blackhole, unreachable, prohibit

Маршрут может и намеренно отбрасывать трафик.

    /ip route add dst-address=10.0.0.0/8 blackhole

| Тип | Что происходит с пакетом |
|---|---|
| blackhole | молча отбрасывается |
| unreachable | отбрасывается, отправитель получает ICMP *host unreachable* |
| prohibit | отбрасывается, отправитель получает ICMP *administratively prohibited* |

Зачем отбрасывать намеренно? Маршрутизатор, которому принадлежит суммарная сеть (например, 10.0.0.0/8 для всех ваших офисов), не должен отправлять трафик в неиспользуемые её части по маршруту по умолчанию: там он будет ходить по кругу между вами и провайдером, пока не кончится TTL. Blackhole для суммарной сети плюс более точные маршруты для существующих сетей останавливают эту петлю. Blackhole также является дешёвым способом отбрасывать трафик в плохую сеть.

> **RouterOS 6:** `type=blackhole|unreachable|prohibit` на маршруте. RouterOS 7 использует `blackhole` как флаг в `/ip route`; другие типы проверьте через `/ip route add ?` на своей версии.

## Лаба 1: треугольник

В первой лабе у каждого из трёх маршрутизаторов своя LAN. Только со статическими маршрутами каждому маршрутизатору нужен маршрут в две чужие LAN: всего шесть маршрутов. Добавьте отказ канала R1–R2, и станет ясно, почему статическая маршрутизация становится мучением по мере роста сети: каждый альтернативный путь нужно настраивать и поддерживать вручную.

# Lesson: Резервирование: distance и check-gateway

При двух путях в одну сеть дайте предпочтительному меньшую distance:

    /ip route add dst-address=192.168.3.0/24 gateway=10.0.13.2 distance=1
    /ip route add dst-address=192.168.3.0/24 gateway=10.0.12.2 distance=2

Активен только маршрут с distance=1. Если **интерфейс ether2 падает** (кабель выдернут), connected-маршрут 10.0.13.0/30 исчезает, шлюз 10.0.13.2 становится недоступным, первый маршрут становится неактивным, и его место занимает маршрут с distance=2. Ничего дополнительно настраивать не нужно.

## Когда канал остаётся up

В большинстве настоящих сетей отказ, который вас волнует, не роняет ваш порт: между маршрутизаторами стоит коммутатор, медиаконвертер или радиомост, или соседний маршрутизатор завис, а его порт продолжает гореть. Ваш интерфейс остаётся *running*, connected-маршрут остаётся, и маршрутизатор продолжает слать трафик в мёртвый канал.

Это исправляет **check-gateway**:

    /ip route add dst-address=192.168.3.0/24 gateway=10.0.13.2 check-gateway=ping

- `ping`: маршрутизатор отправляет шлюзу ICMP echo; `arp`: отправляет ARP-запросы (работает, даже если сосед блокирует ICMP, но только на Ethernet-подобных каналах).
- Тайминги по слайдам курса: проверка каждые 10 секунд, проверка считается неудачной через 10 секунд, и после двух неудач подряд шлюз считается недоступным; один успешный ответ снова делает его доступным. Поэтому переключение занимает примерно 20–30 секунд.
- Когда шлюз не проходит проверку, все маршруты через этот шлюз становятся неактивными, и включается резервный маршрут.

Ставьте check-gateway на основной маршрут. На резервном он необязателен; он полезен, когда и резервный канал может отказать тихо.

## Симметрия

Резервирование должно работать в обе стороны. В лабе у R1 есть основной и резервный маршрут в LAN3, и R3 нужно то же самое для LAN1, иначе ответы продолжат уходить в мёртвый канал. Слайды курса называют это маршрутами по часовой и против часовой стрелки: если R1 отправляет по часовой, а R3 всё ещё отвечает против часовой через мёртвый канал, ничего не работает.

Попробуйте в лабе **Резервирование: distance и check-gateway**: переведите канал R1–R3 в *тихий отказ* и посмотрите на `/ip route print` на R1 до и после добавления check-gateway.

> **RouterOS 6:** те же параметры: `check-gateway=ping|arp`, `distance=`.

## Netwatch как альтернатива

`/tool netwatch` пингует любой хост и запускает скрипт при переходе в up и down. Он может включать и выключать маршруты, что даёт полный контроль, но скрипты сложнее поддерживать. Рекурсивные маршруты (следующий урок) решают самый частый случай без скриптов.

# Lesson: ECMP и распределение нагрузки

Equal Cost Multi-Path использует несколько следующих шагов для одного назначения одновременно.

    /ip route add dst-address=0.0.0.0/0 gateway=172.16.1.1,172.16.2.1

или, в RouterOS 7, два маршрута с одинаковыми префиксом и distance:

    /ip route add dst-address=0.0.0.0/0 gateway=172.16.1.1 distance=1
    /ip route add dst-address=0.0.0.0/0 gateway=172.16.2.1 distance=1

В `/ip route print` оба активны и отмечены флагом **+**.

## Как делится трафик

RouterOS 7 выбирает следующий шаг для каждого потока по хешу адресов пакета (и по желанию портов; ищите политику хеширования multipath в `/ip settings` своей версии). Все пакеты одного соединения идут одним путём, поэтому TCP не видит переупорядочивания. Цена: распределение статистическое, а не точное. Один большой поток использует только один канал.

| Метод | По соединениям | По пакетам |
|---|---|---|
| ECMP | да | нет |
| PCC (mangle, per-connection-classifier) | да | нет |
| Nth (mangle) | да | да |
| Bonding balance-rr | нет | да |
| OSPF (пути равной стоимости) | да | нет |

## ECMP и NAT, два провайдера

ECMP через двух провайдеров с masquerade работает, только если ответы возвращаются тем же путём и каждое соединение сохраняет свой путь. Так как хеш считается по потоку, соединение остаётся на одном провайдере. Но некоторые сервисы (онлайн-банки, игры) не любят пользователей, у которых разные соединения идут с двух публичных адресов. Для распределения между двумя провайдерами с полным контролем курс использует policy routing с mangle (модуль 3).

## ECMP с check-gateway

С `check-gateway=ping` на маршруте ECMP отказавший шлюз убирается из набора, и весь трафик несут оставшиеся.

# Lesson: Рекурсивные маршруты, scope и target-scope

Шлюз не обязан быть подключён напрямую. RouterOS может разрешить его через другой маршрут: это **рекурсивное разрешение next hop**.

    /ip route add dst-address=8.8.8.8/32 gateway=172.16.1.1 scope=10
    /ip route add dst-address=0.0.0.0/0 gateway=8.8.8.8 target-scope=11 check-gateway=ping

Шлюз маршрута по умолчанию 8.8.8.8, это хост в Интернете. RouterOS находит маршрут к 8.8.8.8 (/32 через 172.16.1.1) и отправляет трафик по умолчанию на 172.16.1.1. Для пакетов ничего не меняется; разница в том, что теперь проверяет check-gateway.

## Зачем: проверка настоящего Интернета

С `gateway=172.16.1.1 check-gateway=ping` маршрутизатор узнаёт только то, что отвечает маршрутизатор провайдера. Если провайдер потерял собственный аплинк, 172.16.1.1 продолжает отвечать, и ваш маршрут по умолчанию остаётся активным, хотя ничего не работает.

С рекурсивным маршрутом check-gateway пингует **8.8.8.8 через ISP1** (маршрут /32 привязывает его туда). Когда пропадает Интернет за ISP1, 8.8.8.8 перестаёт отвечать, маршрут по умолчанию становится неактивным, и работу берёт резервный маршрут по умолчанию:

    /ip route add dst-address=1.1.1.1/32 gateway=172.16.2.1 scope=10
    /ip route add dst-address=0.0.0.0/0 gateway=1.1.1.1 target-scope=11 check-gateway=ping distance=2

![У каждого провайдера свой хост мониторинга, привязанный маршрутом /32; маршруты по умолчанию используют эти хосты как шлюзы](/img/mtcre/recursive.svg)

Две детали, которые нужно помнить:

- Трафик к самому хосту мониторинга всегда идёт через его провайдера из-за маршрута /32. Выбирайте хосты, от которых не зависят ваши пользователи, и разные для каждого провайдера.
- Если хост мониторинга упадёт (такое бывает), вы переключитесь без причины. В больших сетях проверяют по два хоста на провайдера.

## scope и target-scope

Какими маршрутами можно разрешать шлюз? RouterOS использует два числа.

- **scope** маршрута: насколько он «далёкий». У connected-маршрутов scope 10, у статических по умолчанию 30.
- **target-scope** маршрута: наибольший scope, который может быть у маршрута, чтобы через него разрешался шлюз *этого* маршрута. По умолчанию 10 для статических маршрутов.

Шлюз разрешается через маршрут, scope которого меньше или равен target-scope.

![Значения scope и target-scope по умолчанию для типов маршрутов, как в слайдах курса](/img/mtcre/scope.svg)

С настройками по умолчанию статический маршрут (target-scope 10) может использовать для своего шлюза только connected-маршруты (scope 10): это обычная, нерекурсивная маршрутизация. Для рекурсии дайте маршруту к хосту мониторинга `scope=10`, а маршруту по умолчанию `target-scope=11` (или больше, лишь бы не меньше scope другого маршрута). Со scope по умолчанию 30 на маршруте /32 маршрут по умолчанию останется недоступным.

Попробуйте разные значения в симуляторе **Рекурсивный следующий хоп**, а затем выполните лабу.

## Что ломает рекурсию

- Рекурсия работает только в таблице **main** (RouterOS 6 говорит об этом прямо; в RouterOS 7 тоже держите маршруты мониторинга в main).
- Маршрут не может разрешаться через самого себя. Если бы 8.8.8.8 был доступен и через маршрут по умолчанию, маршрутизатор охотно использовал бы маршрут по умолчанию для разрешения его собственного шлюза; /32 этого не допускает.
- В RouterOS 7 `/ip route print detail` показывает `immediate-gw` (настоящий следующий шаг) для каждого маршрута; по нему видно, во что разрешился рекурсивный маршрут.

> **RouterOS 6:** синтаксис тот же. RouterOS 6 показывал в `print detail` строку `gateway-status=8.8.8.8 recursive via 172.16.1.1 ether1`.
